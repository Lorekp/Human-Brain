# Balanced Evidence-to-Action Session V1

Status: public-TRAIN development design, not frozen and not spent. Updated 2026-09-04.
This revision plans follow-up work; it does not start implementation or experiments.

## Purpose and evidence boundary

The immediate workload is neutral reading -> delayed fact memory -> a fresh
Python edit -> real execution -> later transfer through **the same persistent
learner**. Provenance revision, one-to-three-hop reasoning, and the broad session
below follow that smallest integrated loop. Coding supplies exact feedback;
language acquisition and retention must also succeed independently.

Neutral frame induction and persistent facts are **mechanisms demonstrated;
integration and robustness pending**. Commits `955b32e` and `4f23658` establish
tiny exact-token, positional, two-slot memory fixtures. They do not demonstrate
broad reading, learned provenance revision, or integrated software competence.
The older `b5ccc73` action bridge still uses answer-supervised upstream frames
and a fixed `SUBSTITUTE -> END` program; its `.unit` fixture is not executed
Python software. See [benchmark status](../benchmark-status.md#language-and-knowledge-lane)
for chronology, controls, and precise claim limits. Existing spent results remain unchanged.

Before selecting or replacing mechanisms, read the
[roadmap architecture policy](roadmap-reading-to-coding.md). It owns the current
neuronal/cell-core commitment, changeable cell/GLIF implementations, and rules
for disclosed hybrid components and contribution comparisons. This plan does
not independently mandate an external store, tokenizer, or pretrained model.

## Immediate development sequence

Use a small reusable TRAIN workload with the following eight stages. This is a
capability sequence, not an already materialized or frozen eight-episode cohort;
declare the concrete episode count, inputs, update points, and resource budget
before implementation. Keep one persistent checkpoint lineage throughout.

| Stage | Work and completion evidence |
| --- | --- |
| 1 | Read independent raw-document examples that support recurring structure; log acquisition without question answers or selected fact labels. |
| 2 | Read further independent examples and acquire fresh facts through that structure; retain custody and count stored lexical bytes. |
| 3 | Interleave unrelated material, then remove the fact-bearing documents from live input; record the resulting checkpoint and delay. |
| 4 | Query those absent-source facts in both learned directions; record first-attempt recall and unsupported/conflicting-query no-action probes. |
| 5 | Attempt a small knowledge-conditioned edit in a real Python workspace and execute it. Only after recording the first attempt may a teacher provide a successful action transition. |
| 6 | Attempt a second independent workspace example, execute, then permit another explicit action demonstration if needed; record learning from its authenticated outcome. |
| 7 | Use an independently ingested fresh fact and renamed workspace to test later code transfer with source documents absent. The learner selects the edit; run the actual Python behavior and inspect the resulting workspace. |
| 8 | After intervening experience, probe earlier fact recall and code/action retention, plus missing-evidence or ambiguous-action no-action cases. |

Raw-document acquisition remains answer-free. Supervised action demonstrations
are allowable research scaffolding and must be labeled separately. Corrections
and demonstrations follow the learner's first attempt, never count as its
success, and do not establish autonomous recovery. Report later transfer from
those lessons separately from first-attempt training performance.

Fork treatment and `NO_UPDATE` from the **same seed checkpoint**, with matched
initial state, observations, tool protocol, and budgets. Treatment may learn at
declared update points; control remains frozen. Keep inference read-only and
bind every update to its observation, actual action, consequence, and parent.
Report language, executable coding, retention, and no-action outcomes separately;
a strong edit score cannot hide failed memory. The first development milestone
requires demonstrated delayed recall, fresh executable transfer, retention, and
appropriate no-action through the same learner, with a measured update advantage
and no decoy modification or hidden retry. Publish failures as well as successes.

For each run record error/STOP distributions, action counts, teacher exposure,
checkpoint age, and resource costs: wall time, peak memory, checkpoint/lexical
bytes, assembly/cell/synapse counts, growth per learned fact/action, and repeated
assembly or rebuild work. Compare with a simple disclosed reference, such as an
exact fact table plus literal-edit rule under the same inputs and execution
checks; its host semantics are a reference contribution, not learner evidence.

## Development pressure and bounded diagnosis

Develop on varied sentence forms, independent names and files, distractors,
document order, and incidental multiple lexical matches. Track each stratum;
unimplemented variation is an explicit failure or limitation. An opaque request
with one query/source coincidence is a legitimate diagnostic control for the
spent persistent V2 interface failure. It is not a general request contract or
an evaluation restriction. The spent V2 record stays immutable; see
[benchmark status](../benchmark-status.md) for the original failure.

When the integrated workload fails, name the failed capability and observation,
then set a time/compute/iteration budget and return criterion for one diagnostic
micro-gate. Return to the workload at that budget boundary, including on failure.
Repeated unresolved failures trigger a research or architecture review against
the roadmap, rather than another sequence of special-case gates.

After the smallest loop works, broaden language variation and memory load, then
add learned provenance revision and source recall, shared one-to-three-hop
composition, and tool-driven recovery. Authentic public reading examinations in
[reading-comprehension evaluation](reading-comprehension-evaluation.md) provide
complementary language pressure; follow that plan's development/held-out split.
Exam items must come from authentic public exams, not LLM-authored substitutes.

## Common observation and feedback contract

The intended integrated interface is `respond(request, documents, files,
tool_events, ablation) -> PhysicalActionDecision`, with raw bytes and opaque
document/workspace records. Documents and files appear throughout; modality
presence must not supply a task label. Host adapters expose environmental
structure and execute selected actions, while the declared learner chooses
answers, paths, values, tool invocations, and no-action. Any richer component
must follow the roadmap's disclosure and contribution-control policy.

Private expectations are evaluator-only. At inference, the interface exposes no
designated answer span, selected relation, target path/value, or candidate patch.
Teacher transitions enter only at declared training updates. Real execution
returns raw output to the learner; the evaluator checks expected behavior and
decoy integrity after action. Multi-action recovery requires the learner's own
diagnostic, interpretation, and repair within a declared action budget.

## Later 24-episode challenge — retained public-TRAIN design

This larger design remains not frozen and not spent. Its evaluator-only episode
descriptions must never become model inputs. All code transfers depend on prose
knowledge; literal substitution bounds the motor scope rather than claiming
broad synthesis. Fifteen episodes emphasize language/knowledge and nine coding.

| Episodes | Required pressure |
| --- | --- |
| 01–04 | Two independent examples for each of two prose surfaces. |
| 05–06 | Neutral ingestion of facts needed after the documents disappear. |
| 07 | First knowledge-conditioned code attempt, then one authenticated teacher transition. |
| 08 | Fresh renamed two-hop language transfer. |
| 09 | Second independent code transition, permitting action-schema promotion. |
| 10 | Fresh paraphrase transfer without shared content n-grams. |
| 11 | Fresh executable code transfer through two scientific relations. |
| 12 | Language transfer with reversed document order and matched distractors. |
| 13 | Counterfactual code transfer: one fact changes both file and value. |
| 14 | Delayed recall from 05–06 with original documents absent. |
| 15 | Three-hop code repair; request names neither file nor replacement. |
| 16 | Emit a revision supported by learned provenance asymmetry. |
| 17 | Apply the revised fact in executable code. |
| 18 | Recall the supporting provenance. |
| 19–20 | Equally supported conflict requires no-action in code and language. |
| 21 | Delayed code/action retention after revision and conflict. |
| 22 | Unsupported language relation requires no-action. |
| 23 | Autonomous two-action recovery: diagnostic, raw output, repair, execution. |
| 24 | Delayed cross-project three-hop language composition. |

Before revision scoring, earlier TRAIN examples must teach a transferable raw
supersession signal through independent consequences. Opaque identities,
document order, age, or append order alone cannot establish truth; equally
supported conflict requires no-action.

The proposed challenge targets remain at least 8/9 language and 6/7 coding
transfer successes, with their minimum accuracy as the balanced score. Revision,
delayed recall and code retention, conflict/unsupported no-action, tool recovery,
and final composition are mandatory. Treatment must exceed the matched same-seed
`NO_UPDATE` arm by at least three language and three coding episodes. Before
adjudication, specify the exact scoring roster and causal predictions for fact
write/retrieval, knowledge-to-action, recurrence, and provenance ablations.

## Reusable development versus frozen adjudication

Reuse development examples and regression tests openly to improve mechanisms;
record exposure and report them as development evidence. A separate adjudication
requires fresh reserved material, a preregistered protocol, and frozen common
architecture/cohort hashes. Its one-shot result is immutable; corrections require
a newly named experiment with fresh material. Public availability does not make
previously used evaluation material fresh. No existing spent artifact is repaired.

Keep protected R5/R6 sealed. The intended order is integrated development and
capability evidence, common architecture freeze, then the required G0 gate before
R5/R6. Follow the roadmap and frozen protocols for their exact admission rules;
this planning revision neither opens protected data nor starts an experiment.
